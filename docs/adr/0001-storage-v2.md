# ADR 0001: Хранилище и формат данных v2.0

- Статус: принято (M1, Variant A)
- Дата: 2026-11-10
- Связано: `docs/SCHEMA-v2.md`, `docs/SECURITY-DATA-v2.md`, `docs/план-перехода-на-v2.0.md`

## Контекст

v1.x хранит все данные в одном `data.json` (полная перезапись при каждом сохранении, полная отдача состояния в renderer по IPC), бэкапы — копии этого файла, опциональное шифрование покрывает весь JSON целиком. Для v2.0 (Variant A) требуются: версионированные миграции 1.x→2.0, вложения, теги/умные списки, статусы/порядок (канбан), календарные выборки, история/статистика, восстановление из бэкапа в UI — при сохранении локальной, офлайн-модели без синхронизации.

## Решение

**На 2.0 принимается JSON v2 как основное структурное хранилище + файловое хранилище вложений.**

- Структурные данные: `data.json` с `version: 2` и версионированной схемой (`meta`, коллекции сущностей, настройки).
- Вложения: содержимое файлов в каталоге `<dataDir>/attachments/` (content-addressed/уникальные имена по решению реализации), метаданные и ссылки — в `data.json`.
- Бэкап/перенос: снапшот включает `data.json` (и необходимые метаданные бэкапа); политика включения `attachments/` фиксируется отдельно (минимум — согласованный перенос каталога данных), pre-migration бэкап создаётся до преобразования.
- Миграции: единый конвейер `read → decrypt → parse → migrate (цепочка версий) → normalize(v2) → validate → save`, с идемпотентными шагами и обязательным pre-migration бэкапом.
- API/сервисы: сохранить фасад `Store`/сервисов и существующие IPC-каналы; новые возможности добавлять расширением контрактов (без ломающих переименований). Полная отдача состояния по IPC допускается на M1, с возможной оптимизацией позже.

**SQLite не выбирается для 2.0:** выигрыш (FTS, индексы, транзакции, диапазонные запросы) признан, но стоимость миграции хранилища, шифрования и бэкап/экспорт формата выше допустимой для безопасного M1. Архитектуру сервисов/нормализации держать достаточно изолированной, чтобы не блокировать переход на SQLite в будущем (репозиторный/адаптерный слой при рефакторинге).

## Последствия

- **Плюсы:** минимальный риск для данных 1.x, переиспользование атомарной записи/backup-подхода, понятный формат для экспорта/отладки, инкрементальная доставка.
- **Минусы:** производительность и запросы (календарь/статистика/поиск) ограничены in-memory обработкой; рост истории/вложений требует дисциплины (лимиты, GC, индексация в памяти).
- **Шифрование:** текущее шифрование — всего JSON; вложения требуют отдельной модели (см. `docs/SECURITY-DATA-v2.md`), на M1 не должно ухудшать существующее поведение.
- **Совместимость:** импорт обязан принимать v1 и v2 через общий конвейер; экспорт по умолчанию v2.

## Альтернативы

- **SQLite в 2.0:** отклонено для M1 из-за объёма изменений и рисков для миграции/шифрования/бэкапов; рассмотреть в post-2.0 при росте данных.
- **Оставить v1 без версионированных миграций:** отклонено, несовместимо с целями 2.0 и безопасностью апгрейда.
