# План перехода на v2.0 (Variant A)

> Локальная эволюция продукта: новая схема/миграции, вложения, теги/умные списки, календарь/канбан, статистика, усиленная модель данных. Без синхронизации, аккаунтов, совместного доступа и смены платформы.

## Уточнения из анализа кодовой базы (важно учесть в плане)

- **Миграции сейчас фактически не работают на старте:** `Store.load()` (`src/main/store.js`) не вызывает `migrateData`; импорт вызывает, но `normalizeData` (`src/main/normalizers.js`) всегда возвращает `version: 1` — реального конвейера `1.x → 2.0` нет. В `load()` есть хрупкость: обращение к `this.backups.*` при восстановлении/`ensureDailyBackup` до инициализации сервисов в конструкторе.
- **Хранилище/перфоманс:** монолитный `data.json`, полная запись/клонирование и полная отдача состояния по IPC; шифрование покрывает только JSON-строку (вложения потребуют отдельного решения).
- **Модель/инварианты:** задачи/подзадачи (глубина 2), напоминания (legacy + `reminders[]`), повторы с автосозданием следующего экземпляра в `TaskService.toggleTask`, runtime-поля `notified*/snoozedUntil`; заметки с `archived`, два типа шаблонов. Нет тегов, вложений, статусов/порядка, истории, сохранённых фильтров.
- **Renderer:** vanilla JS, модули в `src/renderer/modules/*`, единое состояние в `app.js`, списочные представления; есть дублирование/связность логики сохранения и рекурсивной синхронизации подзадач (`app.js` vs `modules/task-modal.js`). Мини-панель — отдельный renderer (`mini.html/js/css`).
- **Тесты:** `tests/basic.test.js` (node:test, `Store`/сервисы/напоминания/повторы), smoke (`src/main/smoke-test.js`, env `MYTASKS_SMOKE/MINI`), e2e на базе smoke-отчёта (`tests/e2e/app.test.js`). Нужны фикстуры миграций и покрытие новых сущностей/видов.

## Вехи (порядок внедрения)

1. **M1 — Безопасный апгрейд:** E0 → E1 → E2 (миграция, v2-ядро, полная совместимость 1.x, pre-migration backup/restore). *Жёсткий гейт перед новыми фичами.*
2. **M2 — Организация:** E3 (теги, умные списки, поиск).
3. **M3 — Планирование:** E4 (канбан, календарь).
4. **M4 — Контент и инсайты:** E5 + E6 (вложения, история, статистика, undo).
5. **M5 — Релиз 2.0.0:** E7 (доки, тесты, полировка, версия/артефакты).

## Рекомендуемые первые шаги (можно брать в работу сразу)

1. **E0.1–E0.2**: ADR хранилища + `docs/SCHEMA-v2.md` и маппинг `status↔done` (иначе E1/E4 расползутся).
2. **E1.1–E1.3**: починить `load()`/конвейер + реальный `migrateData` + `normalizeData v2` с golden-фикстурами v1 (`tests/fixtures`).
3. **E1.4**: pre-migration backup и restore-API (минимальный риск потери данных при всех последующих шагах).
4. **E2.5**: консолидировать сохранение/синхронизацию задач в renderer до массового добавления полей UI.

## Принципы реализации

- Вести миграции и нормализацию как **единственный путь** записи/чтения данных (никаких ad-hoc мутаций мимо `save/normalize`).
- На каждый новый канал IPC — обновлять `preload.js` и держать payload’ы стабильными/обратно совместимыми.
- Любое изменение схемы — обновлять фикстуры миграций и `docs/SCHEMA-v2.md` в том же изменении.
- Перед миграцией — обязательный несгораемый бэкап; при ошибке — не затирать оригинал и давать понятное сообщение/путь отката.
